# ITパスポート出題Slack Bot 開発企画書

Oct 30, 2026 · @takoyakidath

## 企画概要

毎朝7時にITパスポートの問題を1問自動で出題し、スタンプで回答、スレッドで正解と解説を返すSlack Botを開発します。問題と出題予定はWebの管理画面から運営メンバーが編集できるようにします。

| 項目 | 内容 |
| --- | --- |
| 名称（仮） | ITパスポート出題Bot |
| 対象 | ITパスポート対策同好会のSlackワークスペース |
| 利用者 | 同好会メンバー全員（回答）、運営メンバー（問題管理） |
| 開発担当 | 提案者（1名） |
| 進め方 | 最小構成で運用を始め、段階的に機能を追加 |

## 背景と目的

出題を自動化し、運営メンバーが問題作成や投稿準備に使っている時間を、自分自身のITパスポート学習に回せるようにすることが目的です。

**現状の課題**

- 問題の作成・投稿準備を運営メンバーが毎回手作業で行っている
- その分、運営メンバー自身の学習時間が削られている
- 投稿が担当者の都合に左右されると、学習の習慣が途切れやすい

**目指す状態**

- 毎朝決まった時間に問題が届き、メンバーが無理なく毎日1問に取り組める
- 運営は問題の登録と確認だけに集中でき、日々の投稿作業はなくなる
- 同好会全体で継続的に学習できる環境ができる

## 機能要件

実装する機能は4つで、上の3つを最初のリリース（フェーズ1）に含めます。

| 機能 | 内容 | フェーズ |
| --- | --- | --- |
| 毎朝の自動出題 | 毎朝7時（日本時間）に問題を1問、指定チャンネルへ投稿する。出題予定キューがあればその順、なければ未出題の問題からランダムに選ぶ | 1 |
| スタンプによる回答 | 選択肢ア〜エに対応するスタンプをBotが自動で付け、メンバーはそれを押して回答する | 1 |
| 正解・解説の自動返信 | 決まった時刻（例：同日夜）に、出題メッセージのスレッドへ正解と解説を返信する | 1 |
| Web管理画面 | 問題の追加・修正、出題予定のキュー管理を運営メンバーがブラウザから行う | 2 |

**今後の拡張候補（必要に応じて検討）**

- 回答の集計（正答率・回答者数）をスレッドに表示
- 分野別（ストラテジ・マネジメント・テクノロジ）の出題バランス調整
- 個人の連続回答日数や月間ランキング

## 利用イメージ

&#91;embedded content: 1日の流れ · 自動出題から解説返信まで\]

メンバーは朝に届いた問題にスタンプで答え、夜にスレッドで答え合わせをします。運営の作業は、管理画面での問題登録と、指摘があったときの修正だけです。

## 技術構成案

Slack公式のBoltフレームワークを中心に、無料枠で運用できる構成を想定しています。最終的な選定は開発開始時に確定します。

| 要素 | 候補 | 選定理由 |
| --- | --- | --- |
| Bot本体 | Slack Bolt（Node.js または Python） | Slack公式で、メッセージ投稿・スタンプ付与・スレッド返信を標準で扱える |
| 定時実行 | Slackのワークフロー、または cron / スケジューラ | 毎朝7時の出題と解説返信の時刻管理 |
| データ保存 | 問題・出題履歴・キューを持つデータベース。初期問題はIPA公開問題PDFをClaude APIでJSONに変換して投入 | 出題済みの重複防止と予定管理のため |
| Web管理画面 | Bot と同じサーバーで動く簡易Webアプリ | 運営メンバーがブラウザから問題を編集できる |
| ログイン | Googleアカウント（学校アカウント）でのログイン。許可リストの運営メンバーのみ | 管理画面を運営メンバーだけに限定する |
| 実行環境 | 無料または低コストのホスティングサービス | 同好会予算で継続運用できること |

**必要な権限（予定）**：メッセージ投稿、スタンプ付与、スレッド返信。メンバーの個人情報やDMは扱いません。

## 開発スケジュール

動くものを早く出し、運営の皆さんの確認を挟みながら3段階で進めます。各フェーズの具体的な日程は、運営メンバーと相談のうえ決定します。

| フェーズ | 内容 | 完了の目安 |
| --- | --- | --- |
| 1. 試験運用 | 自動出題・スタンプ回答・解説返信を実装し、テスト用チャンネルで動作確認 | 1週間、毎朝欠かさず出題・返信できる |
| 2. 本番運用＋管理画面 | 本番チャンネルで運用開始。Web管理画面で問題追加・修正・キュー管理を可能にする | 運営メンバーがコードに触れずに問題を登録できる |
| 3. 改善 | メンバーの声をもとに集計表示などを追加 | 運営・メンバーからの要望を反映 |

- [ ] 運営メンバーとフェーズ1の開始日を決める
- [ ] テスト用チャンネルを用意してもらう
- [ ] 初期問題（最低30問程度）の準備方法を相談する

## 品質・運用体制

問題は運営メンバーが確認・承認したものだけを出題し、運営の皆さんが安心して任せられる仕組みにします。

**問題の正確性**

- 問題には「下書き」「確認済み」の状態を持たせ、確認済みの問題だけを出題対象にする
- 正解・解説には出典（過去問の回次や参考資料）を記録する欄を設ける
- 誤りの指摘はスレッドで受け付け、管理画面からすぐ修正できるようにする

**障害への備え**

- 出題や返信に失敗したときは、運営用チャンネルに通知する
- 動作ログを残し、不具合の原因を調べられるようにする
- 開発者が対応できない期間に備え、手順書と停止方法を運営メンバーと共有する

## 期待される効果と評価指標

運営の作業時間が減り、メンバーが毎日問題に触れる習慣ができることを効果として見込んでいます。運用開始から1か月後に、以下の指標で振り返ります。

| 観点 | 指標 | 測り方 |
| --- | --- | --- |
| 運営負担 | 毎日の投稿作業にかかる時間 | 導入前後で運営メンバーに聞き取り |
| 学習の継続 | 1問あたりの回答者数の推移 | スタンプ数を集計 |
| 学習の効果 | 正答率の推移 | スタンプと正解を照合 |
| 安定性 | 予定どおり出題・返信できた日の割合 | 動作ログで確認 |
| 満足度 | メンバー・運営の感想 | 簡単なアンケート |

目標値は、運用開始前に運営メンバーと相談して決めます。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 問題・解説に誤りがある | 確認済みの問題だけ出題し、指摘を受けたら管理画面ですぐ修正する |
| 過去問など問題文の著作権 | 出典の利用条件を確認し、必要に応じてオリジナル問題や引用ルールを運営と決める |
| 問題のストックが尽きる | 残り問題数が少なくなったら運営用チャンネルに通知する |
| サーバー停止で出題されない | 失敗時に運営へ通知し、手動で出題できる手段も残す |
| 開発者1人に依存する | ソースコードと手順書を共有し、引き継げる状態にしておく |
| Slackの仕様・料金プラン変更 | 公式の更新情報を確認し、影響があれば運営に早めに相談する |

N高等学校に在学し、プログラミングを中心に活動しています。Bot開発と運営の両方の経験を活かし、実際に運用し続けられる仕組みを目指します。

- **Discord Botの開発・運用**：スラッシュコマンドやNotion APIを使った機能の実装、API連携の不具合調査
- **イベント運営**：N高等学校の磁石祭で運営に携わり、幕張メッセのライブスタジオでMCを担当
